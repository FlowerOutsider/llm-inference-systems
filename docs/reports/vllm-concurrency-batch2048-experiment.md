
# vLLM 并发阶梯与连续批处理实验

## 1. 实验目标

在固定批处理 Token 预算下，测量不同客户端并发度对 vLLM 推理吞吐和延迟的影响，识别连续批处理的吞吐收益、排队代价与适合交互式服务的并发区间。

## 2. 实验环境

- 推理框架：vLLM `v0.8.5`
- 模型：`Qwen/Qwen2.5-0.5B-Instruct`
- 服务模型名：`qwen2.5-0.5b`
- GPU：NVIDIA GeForce RTX 3060 Laptop GPU，6 GiB
- 精度：FP16
- Prefix Cache：启用
- 最大序列长度：2048
- 最大并发序列数：16
- `MAX_NUM_BATCHED_TOKENS`：2048
- 服务部署：Docker Compose
- 服务地址：`http://127.0.0.1:8002`

## 3. 负载与统计口径

每个并发档位执行 3 次独立实验。

- 预热请求：16
- 测量请求：256
- 单请求最大输出：64 tokens
- 共享前缀重复次数：32
- 并发阶梯：1、4、8、16
- 表中每个单元格为中位数 `[最小值, 最大值]`
- 全部实验错误率均为 0%

## 5. 分析

### 5.1 吞吐随并发提升

并发从 1 增加到 16 时，生成吞吐从 136.79 tokens/s 提升到 1088.48 tokens/s。更高并发让 vLLM 有更多请求可合并到连续批中，提高 GPU 的计算利用率。

### 5.2 TTFT 是排队代价的直接信号

TTFT P95 在并发 4 时为 37.11 ms，而并发 8 和 16 时分别升至 70.22 ms 和 149.07 ms。模型开始生成前，请求需要等待调度器形成批次并等待已有批次执行，因此首 token 延迟对排队最敏感。

### 5.3 并发 4 是当前交互式负载的平衡点

并发 4 相比并发 1 显著提高生成吞吐，同时 TTFT P95 只从 34.02 ms 增加到 37.11 ms，E2E P95 反而更低且波动较小。对于交互式聊天类服务，这是当前实验条件下更合理的默认并发目标。

### 5.4 并发 16 是吞吐优先档位

并发 16 的生成吞吐最高，但 TTFT P95 和 E2E P95 分别达到 149.07 ms 与 547.83 ms，并且多次运行的波动更大。该配置更适合离线批处理或对首 token 延迟要求较宽松的场景。

## 6. 结论与建议

在 RTX 3060 Laptop GPU、Qwen2.5-0.5B、FP16、共享前缀和 `MAX_NUM_BATCHED_TOKENS=2048` 的条件下：

- 交互式在线服务建议从客户端并发 4 起步。
- 并发 8 可以作为吞吐和体验之间的折中，但需要确认 TTFT SLO 能接受约 70 ms 的 P95。
- 并发 16 适合吞吐优先场景，不应直接作为低延迟在线服务默认值。
- 结论只对当前模型、硬件、输入输出长度和 Prefix Cache 命中模式有效；上线前应以真实流量分布重新测试。

## 7. 复现

```bash
for concurrency in 1 4 8 16; do
  for run in 1 2 3; do
    python benchmarks/serving/vllm_streaming_benchmark.py\
      --warmup-requests 16\
      --requests 256\
      --concurrency "${concurrency}"\
      --max-tokens 64\
      --shared-prefix-repeats 32\
      --output "benchmarks/serving/results/vllm_concurrency_${concurrency}_batch2048_run${run}.json"
  done
done
```
